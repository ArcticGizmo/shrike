The problem

Raw pointer motion reads as "rough"

In a demo recording the mouse is the narrator, and a hand-driven pointer is full of micro-jitter, overshoots and abrupt direction changes. Played back, it looks nervous — the single biggest tell between a raw screen grab and a produced one.

The fix the good tools use isn't steadier hands, it's post-processing: keep a record of where the pointer actually went, then redraw it along an eased path with a little feedback on each click.

Prior art

A proven pattern, not a moonshot

This is well-trodden ground. The reference is Screen Studio; the same three ingredients recur across the category:

Screen Studio — the reference Cursorful Focusee Tella Screenity
① smoothed / eased motion ② click ripple + press "punch" ③ (bonus) auto-zoom toward clicks

Why it fits Shrike

We already record a clean plate

✦

Most recorders bake the OS cursor into every frame, so faking a nicer one means erasing the real one first. Shrike doesn't. GDI never captures the hardware cursor — we draw it deliberately — so the frames are already a clean plate. The natural design is simply: for this mode, don't draw the real cursor, log its path instead, and paint the pretty one on at export. It's the hide-cursor toggle we just shipped, turned inside out.

The two effects

Smoothing, and a click you can feel

Motion

One-Euro filter

An adaptive low-pass: heavy smoothing when the pointer drifts slowly, low lag when it darts. That adaptivity is what stops smoothed cursors feeling like they're wading through syrup — plain averaging can't do both. Resampled to frame times so it lines up with the video.

Feedback

Ripple + punch

On a logged click, an expanding ring blooms for ~350 ms at the point, optionally paired with a quick cursor scale-down on press. Small, but it reads as intent — the viewer sees where and that you clicked without you narrating it.

One real decision

How the cursor gets composited

Option A · not chosen

ffmpeg overlay layer

Render a transparent cursor-and-ripple layer from the track; let ffmpeg overlay it onto the base clip.

  • + Reuses the export path we already have
  • + Managed code only draws a mostly-empty layer
  • + Fastest route to something demoable
  • − Adaptive auto-zoom is brittle as ffmpeg expressions
Option B · chosen

Managed per-frame pass

Decode → draw the cursor + effects in managed code → re-encode, frame by frame.

  • + Full control; auto-zoom is just a per-frame crop in code
  • + One foundation for cursor + zoom — no mid-feature rewrite
  • − A render pipeline to build (decode side added to our existing encode pipe)

Decided: Option B — auto-zoom is on the roadmap, and eased zoom/pan is natural to compute per frame in code but painful to express as ffmpeg filters. Cursor MVP first, zoom later on the same rails.

Eyes open

The genuinely fiddly parts

01

Coordinate mapping

Track is virtual-screen physical px; the region is a sub-rect trimmed to even dims and maybe downscaled, possibly across mixed-DPI monitors. Landing the cursor exactly where it was is the fiddliest bit.

02

Timing & pause

Track timestamps must ride the recorder's own clock so they align to frame PTS — including across pause/resume, which excludes time from the video.

03

Cursor asset

A crisp vector cursor with a correct hotspot beats reusing the OS arrow — and it's what makes the result look intentional rather than pasted.

Proposed MVP

Smallest thing that proves the "wow"

In scope

  • Log the mouse track at capture (path + clicks)
  • One-Euro smoothing, resampled to frame times
  • A single synthetic cursor drawn over the frames
  • Click ripple effect
  • Composite via Option B (managed per-frame)
  • Sensible fixed defaults — no tuning UI yet

Deferred

  • Auto-zoom toward click clusters
  • Cursor size / press-punch controls
  • A tuning UI in the timeline editor
  • Custom cursor themes
  • Live real-time smoothed preview
