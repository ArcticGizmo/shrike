The shift

From a tuning panel to an editing surface

Everything works today — but it's configured, not authored. One CursorCompositor bakes the cursor, ripples, and zoom together, driven by a few sliders that apply to the whole clip. That ceiling is low: you can't say zoom here, to this, this fast, and there's nowhere to hang the next effect.

Today Global & baked

A tuning panel: Smoothness, Size, Ripple, Zoom on/off + max. One setting per clip.

Zoom is inferred automatically from click clusters — not directable.

Effects live inside one compositor class; adding one means editing it.

Next Placed & composable

Effects are events on lanes — placed in time, dragged, resized, shaped.

Each effect type is independent: its own model, resolver, and renderer.

The compositor becomes a chain — effects stack in order, cheaply added.

The architecture

One path from event to pixels — and to the preview

The rails already exist. A non-destructive Timeline maps edited time to source time; a FrameCompositePipeline decodes → composes → encodes in one pass. Every effect plugs into the same four-step path, and the resolved per-frame data feeds the export and the live preview from a single source of truth.

Cursor, ripples, and zoom already run this path — the smooth-cursor work built the rails. The vision is to make them authored and the pattern repeatable.

The leverage

Adding an effect is five known parts

Because the path is fixed, every new effect is the same shape of work — and most of it is small, pure Core code that's easy to test. The lane UI (step 5) is built once as a framework and reused by every effect after the first.

Event model — Core record

The typed thing on the lane: what it carries and when. e.g. a target rect + easing for zoom, a glyph + duration for a keystroke.

Resolver — Core, headless-tested

Events → one input per output frame, riding the timeline's kept ranges. Deterministic and unit-tested, exactly like AutoZoom today.

Compositor — Core IFrameCompositor

Consumes the per-frame input and draws or transforms the frame. Slots into the chain in a defined order (transforms before overlays).

Preview renderer — App PreviewSurface

Draws the same input live so it's visible while editing. Non-negotiable — the project rule is every effect shows in the preview.

Lane UI + persistence — App, reused framework

Create / drag / resize events on the lane, edit them in an inspector, save to the clip's sidecar. Built once; every later effect gets it free.

The route

Build the platform by shipping one effect through it

No big-bang rewrite. Prove the model with authored zoom, extract the framework as it earns its place, then fan out.

Phase 0 · foundation

Extract the compositor chain

Split today's monolithic CursorCompositor into ordered, composable IFrameCompositors and retrofit cursor, ripple, and zoom as the first three effects. Behaviour-preserving; unlocks stacking.

Phase 1 · prove it

Authored zoom, end-to-end

The first placed effect: a zoom lane with target-shape + easing, resolved to a per-frame viewport, previewed live. Detailed in the timeline-based zoom plan. Retires auto-zoom to an optional "suggest from clicks" generator.

Phase 2 · generalise

The lane framework

Lift the zoom lane's create / drag / resize / inspect + sidecar persistence into a reusable lane framework, so the next effect is mostly Core code.

Phase 3 · fan out

Second effect, cheaply

Add keystrokes or callouts to validate that a new effect really is just five small parts — the proof the platform pays off.
